## Core Mechanism

先复习三条精确规则（第一讲已建立）：

1. Python `list` 是**动态数组**：底层是连续内存，存的是对象**引用**（指针），可异构。
2. **自动扩容**，`append` 均摊 O(1)；随机访问 O(1)；头部/中间插入删除 O(n)；`in` 查找 O(n)。
3. 赋值是**别名**不是拷贝；`*` 复制嵌套列表会共享内层引用。

本讲深入三条新规则：

**规则 4：扩容不是"翻倍"，而是"过度分配"（over-allocation），增长率约 12.5%。** CPython 的 `list_resize` 在容量不足时申请 `newsize ≈ old + old/8`（小列表额外加几项），空闲容量呈几何级数增长。均摊 O(1) 的数学直觉：扩容成本 O(n)，但发生频率随 n 几何级数递减——每次扩容后要积累约 n 次 append 才会再次触发，总成本 O(n) 摊到 n 次操作上就是 O(1)。

**规则 5：连续内存带来"缓存局部性"（cache locality）。** 相邻元素在物理内存中相邻，CPU 按 cache line（通常 64 字节）成块加载，顺序遍历时一次加载喂饱多次访问。这是数组比链表顺序遍历快几个数量级的根本原因之一，也是树、图等结构用"数组扁平化"存储的动机。

**规则 6：list 存的是引用，遍历有解引用成本。** 每次 `arr[i]` 要经过"索引计算 → 读指针 → 跳到对象内存"两步。需要紧凑数值存储时用 `array.array`（每元素是原生 C 类型，如 4 字节 int）或 `numpy.ndarray`；需要频繁两端操作时用 `collections.deque`（双端 O(1)，代价是牺牲 O(1) 随机访问）。

## Analogy

**一列连座的电影院**：

- 座位号连续（连续内存），你报出 7 号座，检票员直接走到第 7 个座位（随机访问 O(1)）。
- 相邻座位的人一起入场检票（cache line 成块加载）——查票的人一次性核对一整排，比逐个到不同楼层找散客快得多（缓存局部性）。
- 上座率超了，影院搬到更大的厅，整排椅子连人一起搬（扩容）。

**这个类比不覆盖的地方**：影院座位是固定的（不能任意扩容换厅规模按需精确调整），而动态数组每次扩容是精确的 12.5% 增量；另外影院的"人"是真实的观众（元素本身），而 Python list 里的"人"其实是一张座位号→人脸的索引卡（引用），卡片可以指向任何类型的人。类比中"搬到更大的厅"在真实实现里不需要整排重排座位号——因为索引是相对地址算出来的，搬厅后按新地址计算即可，用户无感知。

## Code Example

```python
import sys, timeit, random
from array import array
from collections import deque

# 1. 观察过度分配：内存跳跃式增长（每次扩容约 +12.5%，不是 +1）
lst = []
prev = 0
for i in range(100):
    lst.append(i)
    size = sys.getsizeof(lst)
    if size != prev:                      # 只在扩容瞬间变化
        print(f"len={len(lst):3d}  内存={size} 字节")  # 64 位 CPython：空列表开销 56 字节
        prev = size

# 2. 紧凑存储：array 每元素 4 字节，list 每元素 8 字节引用 + 对象本身
a = array('i', [1, 2, 3])                 # C 语言 int 数组，元素在内存中连续且紧凑
l = [1, 2, 3]
print(f"array: {sys.getsizeof(a)} 字节 | list: {sys.getsizeof(l)} 字节")

# 3. deque：两端操作 O(1)
d = deque([1, 2, 3])
d.appendleft(0); d.popleft()              # 都是 O(1)；list 的 pop(0) 是 O(n)

# 4. 缓存局部性：同样的求和，乱序内存明显更慢
n = 1_000_000
ordered = list(range(n))
shuffled = [x for x in ordered]; random.shuffle(shuffled)  # 引用顺序乱，对象地址乱
t1 = timeit.timeit(lambda: sum(ordered), number=20)
t2 = timeit.timeit(lambda: sum(shuffled), number=20)
print(f"连续内存遍历: {t1:.3f}s   乱序内存遍历: {t2:.3f}s")  # 数值随机器/版本变化，看趋势
```

**Walkthrough**：

- **第 1 段**：`sys.getsizeof` 输出只在扩容瞬间跳跃。输出序列形如 `内存=72 → 104 → 136 → 200 …`，容量按约 1.125 倍增长而非每次 +8 字节。这就是"均摊 O(1)"的来源：扩容代价 O(n) 但被之间的大批 O(1) append 摊平。
- **第 2 段**：同样三个元素，`array` 只占 16 字节（头 + 3×4），`list` 要 80+ 字节（引用数组 + 每个 int 对象）。数值密集运算场景（图像、矩阵）用 `array`/`numpy` 可省一个数量级内存。
- **第 3 段**：`deque` 是双端链表+块结构，`appendleft`/`popleft` 都是 O(1)；用 list 模拟队列（`pop(0)`）是 O(n)，大流量下会明显卡顿。
- **第 4 段**：`ordered` 与 `shuffled` 元素值相同、长度相同，唯一区别是遍历时解引用到的对象地址是否连续。连续地址命中 cache line，明显更快——这是"为什么数组结构好"的物理根源。

## Common Misconceptions

1. **以为 Python list 是链表** —— 不是。list 是动态数组（连续内存 + 引用），支持 O(1) 随机访问；真正的链表在 Python 标准库里没有直接等价物，`deque` 才是双端链表思想。
2. **以为 `append` 严格每次 O(1)** —— 单次扩容是 O(n)，均摊才是 O(1)。程序如果知道最终规模，预先用 `[None] * n` 分配好可避免扩容开销。
3. **大列表频繁切片** —— `arr[1000:2000]` 复制出新列表 O(1000)；只想看一眼用下标遍历，别在循环里反复切片。
4. **用 `list` 当队列** —— `pop(0)`/`insert(0, x)` 都是 O(n)；要么用 `deque`，要么用"指针游标"标记头部。
5. **认为 `sum`/`in` 的复杂度与语言无关** —— Python 的 `in` 对 list 是 O(n)，对 `set`/`dict` 才是 O(1)（哈希表，后续主题）。

## Socratic Check

1. 已知 `append` 均摊 O(1)。如果我在循环开头先用 `lst = [None] * 1000000` 预分配，再逐个 `lst[i] = x` 赋值，和直接 `for` 里 `append` 相比，谁快？为什么？
   > **答案**：预分配更快。`append` 版本在接近容量上限时会触发多次 12.5% 的扩容搬迁（虽然均摊 O(1)）；预分配完全避免了扩容，且 `lst[i] = x` 是纯索引赋值。代价是提前知道规模。
2. `array('i', [1,2,3])` 和 `[1,2,3]` 都能索引访问，为什么复杂系统里大数据集普遍选前者？
   > **答案**：内存紧凑（每元素 4 字节 vs 8 字节引用 + 对象头），连续内存缓存友好，遍历吞吐量高得多；代价是元素必须同类型（C int），失去异构能力。

## Quick Summary
- list 扩容是 ~12.5% 的**过度分配**，均摊 O(1)；预分配可完全避免扩容
- 连续内存带来**缓存局部性**——这是数组性能优势的物理根源
- list 存引用有间接成本；数值密集用 `array`/`numpy`，两端操作用 `deque`
- 遍历解引用的内存乱序度直接影响耗时，同一份数据换个布局可能慢数倍
